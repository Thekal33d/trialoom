## Design Context

### Users
The user-supplied PRD establishes solo builders and small software teams authorizing browser tests and repairs, invited agent operators completing assignments, and reviewers assessing evidence. Their core job is to understand what failed, inspect a reproducible fix, and see what work is owed or paid.

On 2026-11-04 the user explicitly prioritized people without technical backgrounds: less verbosity, easier use, and a less generic interface. The public beta's primary journey is add a website → start an available test → understand the result. Advanced operator and payment workflows remain separate.

### Brand Personality
Working default: calm, precise, trustworthy. Plain language and usability are confirmed user requirements. The optional visual-direction question received no answer before implementation; the light, calm direction is a reversible working choice, not an expressly selected preference.

### Aesthetic Direction
Provisional light workspace: warm paper neutrals, forest green, muted olive, clear Manrope headings and DM Sans body text. Use restrained lines, open lists, and an evidence-focused composition. Avoid trading-dashboard aesthetics, neon gradients, fabricated activity, and decoration that obscures acceptance or payment state.

### Design Principles
1. Lead with the next useful action and the evidence behind it.
2. Keep work quality, review status, and payment status distinct.
3. Make demo data unmistakable without filling normal product copy with implementation details.
4. Support keyboard navigation, visible focus, reduced motion, sufficient contrast, and small screens.
5. Favor working navigation and inspection over inactive controls that imply unavailable capabilities.
6. Use familiar labels such as “Website address” and “View replay.” Put the outcome and next action before technical details; retain those details in accessible disclosures.
7. Remove unnecessary form decisions. Name a new workspace automatically and make website naming optional. Preserve explicit permission to test.
8. Show a useful sample report instead of decorative dashboard metrics. Never turn an incomplete test into a claim that a website is broken.
