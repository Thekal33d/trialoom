## Verified provider seam

The product-side preparation accepts at most 12 closed observations: HTTP status, count agreement, navigation, denied-request count, infrastructure blockage or recorded boolean browser checks. No free-form labels, URL, raw trace, page text, account identity, credentials or private source can be supplied. References are generated by position and the canonical input is hashed. This limited projection trades richer context for a narrow privacy boundary.

The observed quote names the pinned service URL, token, gateway payee and USDC signing domain. It is evidence of a price offer, not settlement or output. Run `npm run buy:quote-report` to refresh the same public-safe example. It first reads the live catalog and validates model, output limit, method, URL and availability, then sends exactly one unsigned request. No signer, payment header or wallet is available to this path. Catalog and quote bodies are bounded; redirects are refused. The private detailed response goes under ignored `artifacts/buy-reports/`.

Generated output must be complete JSON with bounded title, explanation, next step and references that exist in the original projection. Truncated responses, unknown references, added decision fields, known secret shapes, URLs and markup are refused. ## Completed evidence binding

Migration `0022_buy_report_inputs.sql` stores one immutable input per free test, service and template version. Preparation verifies the source's canonical hash, terminal outcome and confirmed cleanup. Owner-scoped preparation checks current workspace access on every retry. The local free worker also prepares finished results and catches up after a restart; preparation errors are logged with a fixed code and do not hide the browser result. No preparation path calls a provider or reserves/spends money.

`free-checks-v1` takes only the recorded homepage, navigation (sample only), scope and infrastructure booleans. It does not invent HTTP codes, counts or a reason for a check that did not pass. The prompt explains these limits. Missing, duplicated or inconsistent checks fail closed. Results whose checks all pass are recorded as skipped with no provider request body. Cancelled, interrupted, unfinished and corrupt results cannot create a request.

Prepared inputs fix the exact canonical request body, request hash, projection hash and original result hash before any future purchase. Concurrent preparation returns the same identity; changed inputs cannot replace it. Database ownership/source guards and immutability protect the binding. ## Sponsored purchase journal

Added 2026-11-03 (`0023_sponsored_purchases.sql`, [`src/server/sponsored.ts`](../src/server/sponsored.ts)). **The code path from a prepared report to a settled payment exists and is checked; nothing has been bought, because no sponsor wallet is funded.** `sponsored_budgets` is seeded at zero, so the default adapter refuses every purchase with `sponsor_wallet_unavailable` and the worker does not even try until `sponsorBudgetFunded` is true.

The journal is deliberately not the ALPHA-09 resource ledger. That one ends in a builder reimbursement; this one has **no column, nullable or otherwise, that reaches `payables`**. A free test's explanation cannot become a customer charge because there is nowhere to record one.

What the database enforces rather than the worker remembering:

- **One prepared report, one purchase.** `report_input_id` is `UNIQUE`, and a trigger refuses any purchase whose report input is not `prepared`, is for another account, or carries a different request hash. An all-passing test is recorded as `skipped` with no request body, so it can never be bought.
- **A ceiling that cannot be exceeded.** `quoted_units <= ceiling_units` and `cost_units <= ceiling_units` are checks; the per-report ceiling is 10,000 base units, the reviewed quote. A settled cost above it is held as uncertain with its reservation intact rather than clamped, because recording less than was taken would hide it.
- **Two allowances, both atomic.** The platform's own headroom and one account's daily spend are read under the budget's row lock inside the same transaction that reserves, so a race cannot spend the same headroom twice. A purchase holds its whole ceiling until it reconciles, then holds what it cost.
- **Identity is immutable.** The intent key, report, request hash, ceiling, token, payee and spend day never change, and a recorded cost or transaction hash is never rewritten.

Work state and payment state are kept apart by a `delivery` column. Reconciliation rewrites `state` and clears `reason`; it does not touch `delivery`, so a purchase that paid for an answer nobody can use still says `unusable` after the money is recorded as spent. An explanation that fails `parseBuyExplanation` — a reference to evidence that was never supplied, unsafe text, a truncated response — is exactly that case: the reported cost is recorded separately, no output row is written, and the purchase is `failed` with `output_unusable`.

An uncertain answer is never bought again. The reservation is held, the outbox job asks the token whether value moved, and an unresolved answer reschedules without spending the attempt limit — retiring the job would strand the reservation with nothing left to free it. Only a settled or unsettled reading moves money out of reserve.

The request that was prepared is the request that is paid for. Before quoting, the body is rebuilt from the input's own observations and compared against the hash the immutable row fixed; a body that no longer reproduces refuses with `REQUEST_CHANGED` rather than sending something else.

A public user supplies none of this. `purchaseSponsoredReport` takes a report input id and an adapter — no model, endpoint, payee, wallet or amount — and every one of those comes from the pinned `buyReportService` constant.

Thirteen checks cover it, each verified to fail against the defect it describes: three deliberate mutations (reconciliation overwriting `delivery`, the daily allowance unenforced, an uncertain outcome freeing its reservation) were each caught by the check that names them.

## Paying: the x402 client

Added 2026-11-03 and corrected 2026-11-04 ([adapter](../src/server/buy-x402.ts)). The local signer is configured, the wallet holds 166,000 USDT base units, and the existing budget authorizes 50,000 units total / 20,000 per account per day. Fresh read-only checks found zero reserved or settled units and no purchase rows. The hosted signer remains unconfigured. Funding is sufficient for the first bounded proof; useful paid output is still absent.

**A payment here is a signature, not a transaction.** USDC on Celo implements EIP-3009: the payer signs `transferWithAuthorization` off chain and buy's facilitator submits it and pays the gas. Read from the token on 2026-11-03 rather than taken from documentation:

```
name                                 USDC
version                              2
decimals                             6
DOMAIN_SEPARATOR                     0xb2ce31d2838445fa765a491f550e7c78ac7280ab0f3bc9d6063a86df9c3fb578
TRANSFER_WITH_AUTHORIZATION_TYPEHASH 0x7c7c6cdb67a18743f49ec6fa9b35f50d52ed05cbed4cc592e13b44501c1a2267
```

The typehash equals the canonical EIP-3009 one, `authorizationState` answers, and the domain rebuilt from the quote's own `extra` (`{"name":"USDC","version":"2"}`) reproduces `DOMAIN_SEPARATOR` exactly. The adapter performs that last comparison **before every signature**: a quote can claim any domain it likes, and signing against an unverified one is how a signature ends up valid somewhere nobody intended.

### What the live gateway answers

An unsigned request on 2026-11-03 returns HTTP 402 with the v1 envelope in the body and a v2 envelope in a `payment-required` header, listing three offers — USDC, USDT (`Tether USD`, version 1) and USAT (`Tether America USD`, version 1) — all at 10,000 base units to `0x20faAca5F980E29639A0FCC6dcA6988E18ed333B`.

**All three are accepted.** Read from the tokens the same day, each is six decimals, carries the canonical EIP-3009 typehash, and answers `authorizationState`, so the signing and reconciliation paths are identical for all of them and the price is the same cent either way:

| | address | decimals | EIP-712 domain | `version()` on chain |
| --- | --- | --- | --- | --- |
| USDC | `0xcebA…118C` | 6 | `USDC` / `2` | yes |
| USDT | `0x4806…3D5e` | 6 | `Tether USD` / `1` | **none** |
| USAT | `0xD2ab…F771` | 6 | `Tether America USD` / `1` | **none** |

USDT and USAT have **no `version()` method**, so a token cannot be asked what its domain version is and the only other source is the quote. That is why the domain is taken from this pinned table rather than from the offer, and then checked against the token's `DOMAIN_SEPARATOR`: the check needs no `version()`, and an offer claiming a domain its token does not have is refused before anything is signed. The payee is pinned for all three, so a changed recipient is still a refusal.

Which one is used is decided by what the sponsor wallet actually holds, read from the tokens at quote time. Holding none of them in the quoted amount refuses with `sponsor_wallet_unavailable` — a far more useful thing to say than a verification failure from the gateway.

Which request header the gateway reads was settled by probing with a **deliberately expired authorization from a throwaway key**, so verification had to fail before anything could settle:

| header | answer |
| --- | --- |
| none | `payment_required` |
| `X-PAYMENT` with the v1 payload | `verify_payment_failed: expired` |
| `PAYMENT-SIGNATURE` with the v2 payload | `invalid PAYMENT-SIGNATURE: accepted is missing` |

The v1 path reached the validity-window check, which means the signature recovered and the domain and authorization fields parsed. That is what the adapter implements. The v2 path is available and additionally wants the chosen requirement echoed back as `accepted`; it is recorded here rather than implemented, because it has not been verified end to end.

### The nonce is the payment's identity

The EIP-3009 nonce is derived from the immutable purchase intent. The original payer is persisted; key rotation does not change the wallet checked during reconciliation, and a different signer cannot pay an already-quoted request. The signature's `validBefore` is the persisted expiry rounded down to seconds; RPC latency and a short remaining window cannot extend it. An expired or unbounded quote is refused before signing. Every HTTP error after dispatch retains the reservation, including a reported verification refusal: an HTTP response does not revoke the signed bearer authorization.

Reconciliation always asks Celo, including after a successful provider answer. It checks chain 42220, reads authorization state at one finalized block, and compares expiry with that block's timestamp. An unused authorization cannot release funds merely because the local clock passed expiry. A consumed nonce alone is insufficient, since cancellation can consume it too. The adapter finds the exact `AuthorizationUsed` event in the bounded authorization window and verifies a successful canonical finalized receipt with the pinned token, payer, payee and amount. Missing, mismatched, cancelled or unavailable evidence stays unresolved without another purchase.

Migration `0024_sponsored_settlement_evidence.sql` separates immutable provider-reported cost/hash from verified cost/hash and allows delivery to survive uncertain or unpaid settlement. It refuses to upgrade an existing purchase journal automatically: legacy signatures could outlive recorded expiry and legacy reconciliations trusted HTTP success, so such rows need an independent audit with old workers stopped. The checked local database has no purchases. Reconciliation releases or settles a reserve only once, including repeated job delivery.

### Attribution cannot ride on this, and does not need to

Because the facilitator sends the transaction, this wallet's calldata never exists, and Celo's own documentation says facilitator-side tagging of x402 settlements is not live yet. The adapter therefore attaches **no** attribution tag, deliberately and with the reason in its source. The on-chain `Transfer` still has our wallet as its `from`, and the submission records that wallet. See [HACKATHON.md](HACKATHON.md).

## What the builder sees

The observed checks stay where they were, above and unchanged. Underneath them sits what was bought, in a quieter panel headed **"What this looks like"** and labelled **"Not a test result"**. It carries a title, a summary and a next step, then **"Derived only from"** — the exact observations the explanation cited, by the positional refs `prepareBuyReport` generated, each shown with its real passed-or-blocked state. A claim that cannot name an observation on that list never appears, because `parseBuyExplanation` refuses the response before it is stored.

Beneath it: *"Written by an external service at Trialoom's expense, from the checks listed above and nothing else. No URL, page content, trace or account detail left this product. It is a suggestion, not a finding, and it cannot change a result."*

The states a builder can land in each say what is true rather than showing an empty space:

| State | What the panel says |
| --- | --- |
| all checks passed | nothing at all — there is nothing to explain, and that is a result |
| prepared, not yet bought | an explanation is being bought; the checks are the result either way |
| refused | none was obtained; the checks are unaffected and nothing was charged |
| unusable response | the requested answer could not be used, so it is not shown; payment is independently reconciled |

**A limitation found while building this.** `sponsored_purchases.report_input_id` is `UNIQUE`, which guarantees one report never authorizes two purchases — but it also means a purchase refused for a transient reason, a gateway outage at the wrong moment, permanently denies that report an explanation. The panel says so honestly rather than implying one is still coming. Allowing a fresh attempt after a refusal that paid nothing would need a schema change, and it is not made here.
