The event rules state that "your project will only be valid with an ERC-8004 identity", and that the agent's wallet must be added to the entry with its identity registered **from that wallet** before 2026-11-09 09:00 GMT / 10:00 Africa/Lagos. Trialoom has no agent wallet and no identity yet, so this records what is verified, what is drafted, and what is still missing.

## Verified on 2026-11-02

The Celo mainnet Identity Registry is **`0x8004A169FB4a3325136EB29fA0ceB6D2e539a432`**. Two independent sources agree — the [erc-8004 team's contracts repository](https://github.com/erc-8004/erc-8004-contracts) and [Celo's own documentation](https://docs.celo.org/build-on-celo/build-with-ai/8004) — and the address was then checked against the chain rather than taken on trust:

```
chainId      : 42220
code present : true
name         : AgentIdentity
symbol       : AGENT
```

It is an ERC-721 with URIStorage behind a small proxy. The Celo **Sepolia** registry is `0x8004A818BFB912233c491871b3d84c89A494BD9e`; testnet references are allowed in the repository but only mainnet transactions count.

The registration file format comes from [the ERC itself](https://eips.ethereum.org/EIPS/eip-8004). The on-chain `agentURI` must resolve to that file and may use any URI scheme, including `https:`, `ipfs:` and a base64 `data:` URI, so a registration does not depend on having a domain. The file links back through `registrations`, each entry carrying an `agentId` and an `agentRegistry` written as `{namespace}:{chainId}:{identityRegistry}` — here `eip155:42220:0x8004A169FB4a3325136EB29fA0ceB6D2e539a432`.

The user supplied **`0xf8Ff4F7C83404e04506785b7DFDf838CA75C22ae`**. It is the wallet the entry names and the wallet the registration must come from. Its private key stays with the user: no key for it is held in this repository, in its environment, or by this session, and the registration transaction is theirs to send.

Two consequences follow. Gas is covered: `register()` estimates **108,899 gas**, about **0.022 CELO** at the 202.5 gwei observed, against a balance of 10. Paying is not: **0 USDC means no buy call can be made from this wallet yet**, and BUY-01's first purchase needs it funded. That is a separate gate from identity.

Simulating `register()` from this address against the registry returns agent id **10026**. A simulation is not a reservation — someone else registering first moves the number — so the id is read from the receipt rather than assumed. `register(string agentURI)` simulates equally well; `totalSupply()` reverts, so the registry is an ERC-721 without enumeration.

## The chicken and egg, and how to resolve it

`agentId` only exists after registering, and the file is supposed to contain it. The ERC allows for this: `register()` with no argument, then `setAgentURI(agentId, uri)` once the file is published with the id in it. The order is therefore:

1. ~~Decide the agent wallet.~~ Done: `0xf8Ff…22ae`, above.
2. `register()` from the agent wallet. Calldata is the bare selector `0x1aa3a008`; the receipt carries the agent id.
3. Put that id into `registrations` in [`public/agent.json`](../public/agent.json) and encode the file as a `data:application/json;base64,…` URI — 853 characters at the file's current size.
4. `setAgentURI(agentId, uri)` from the same wallet. Its gas cannot be estimated beforehand, because the call reverts until the token exists.

**Hosting is not on this path.** A `data:` URI resolves without a domain, so the identity can be registered before FREE-03 exists and the URI replaced with `https://<domain>/agent.json` later by calling `setAgentURI` again. Waiting for hosting would put a mandatory requirement behind an optional one.

## Registering it

`npm run identity:register` opens a console on loopback that does the whole sequence. It reads the wallet, its CELO balance, whether it already holds an identity, the registry, the exact calldata and the estimated cost, and **sends nothing until the person at the keyboard presses the button**. On a press it sends `register()`, reads the agent id out of the token's own `Transfer` log rather than from a simulation, writes that id into `public/agent.json`, encodes the file as a `data:` URI and sends `setAgentURI`.

It refuses to start without `TRIALOOM_SPONSOR_AGENT_KEY` — the same key, because the entry names one agent wallet and the rules require the identity to come from it — and it never prints the key.

**Why the id comes from the receipt.** A simulation on 2026-11-03 returned agent id 10026 in the morning and 10031 a few hours later: five identities were registered in between. A simulated id is a reading of a moving number, never a reservation.

## What is still missing, and why it is blank rather than guessed

[`public/agent.json`](../public/agent.json) is the real file, not a sample, and the fields that are not yet true are **empty rather than filled with a plausible value**:

| Field | Why it is empty |
| --- | --- |
| `image` | No hosted image exists. An ERC-721 app would show a broken link. |
| `services` | Each entry needs a resolvable `endpoint`. Nothing is deployed, so there is no endpoint to name. |
| `registrations` | **Now filled**: `agentId` 10031 against `eip155:42220:0x8004A169…A432`, as published. |
| `active` | `false` until the service actually answers. Claiming otherwise would be the one field a reader checks first. |
| `x402Support` | `false`. Trialoom pays for services; it does not charge over x402. |
| `supportedTrust` | Empty is meaningful: the ERC says the identity is then used for discovery only, which is what this is. |

Publishing it as it stands is honest and registers a discoverable identity. Filling `services` and setting `active` waits on FREE-03 hosting; `setAgentURI` can be called again then, and a hosted `https:` URI would also be far cheaper to store than the 853-byte `data:` URI this one cost 675,343 gas to publish.
