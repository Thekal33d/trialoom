Two further points were confirmed on the 2026-11-02 reading. The page lists submission contents as a public GitHub repository, and for Build with buy a statement of the services used with proof of payment; it **does not explicitly require a hosted demo, a video or a deployment**, so hosting is a product gate rather than a submission one. And "code is written during the hackathon" is satisfied: kick-off was 2026-10-06 and this repository's first commit is `22e6ce0` on 2026-10-26.

**The submission form asks for more than the public page lists.** `loops project fields` on 2026-11-02 reports six required fields: `name`, `description`, `repoUrl`, `screenshots` (at least one), `demoUrl` (live demo or website link), and the extra field `agent-wallet`. Two corrections follow. A **live demo URL is required**, so FREE-03 hosting is a submission gate after all, not only a product one — an earlier reading of the public page concluded otherwise because the page does not list it. And the repository field says "GitHub repo (**private repos supported**, judges get read access)", so the repository need not be public, but it does still need to be GitHub.

**Unresolved, and it has to be resolved before the first paid call.** The public page says an attribution tag is "not required for Build with buy". The event skill installed on 2026-11-02 (`npx loopshouse add agents-on-open-rails`) says the opposite as a general rule: "A transaction the project sends is credited to this entry only if its calldata carries the entry's ERC-8021 attribution tag. A transaction sent without the tag can never be credited later: there is no backfill." The Build with buy bounty itself is scored on "verified paid calls from the project's **tagged wallet** on Celo mainnet". A third source of ambiguity: the page states attribution tags are not yet supported on x402 and a PayTo wallet address is required there instead, and buy settles over x402.

**Resolved on 2026-11-03, against the live gateway and Celo's own documentation: a buy x402 payment cannot carry this entry's tag, and does not need to.** USDC on Celo implements EIP-3009, so a payment is a *signature*, not a transaction — the payer signs `transferWithAuthorization` off chain and buy's facilitator submits it and pays the gas. Our wallet therefore never sends a transaction, so there is no calldata of ours to tag. Celo's own x402 documentation states that facilitator-side tagging of x402 settlements is **not live yet**, which closes the remaining possibility from the other end. What does exist is the on-chain `Transfer`, whose `from` is our wallet, and the submission form asks for exactly that wallet — which is consistent with the sponsor SDK's own instruction to credit `sender` rather than the transaction's `from`, and with Celo's note that crediting is resolved at the indexer layer. The tag stays wired into the Remesso settlement client, where we do send transactions; it is deliberately **not** attached to the x402 path, because a tag that would be dropped is worse than none. If the organisers credit Build with buy only by calldata tag, no entry paying through buy can qualify, which is itself worth asking them.

The earlier reasoning, kept because it is what led here. A knowledge-graph query against the buy sponsor on 2026-11-02 advanced this without closing it. The attribution SDK documents a **Schema 2 role-based tag** that is "the shape used by payment facilitators (e.g. x402 settlement services) that submit transactions on behalf of an app", encoding the app, the facilitator and optionally the paying client separately — and it says to "credit `sender`, not the transaction's `from` — `from` is the bundler". Celo's own documentation adds that "whether a code gets credited on a leaderboard or rewards program is resolved at the registry/indexer layer, not at the tagging step". So for an x402 call the settling transaction is not ours to tag, Schema 2 exists precisely for that case, and crediting is an indexer decision. What remains unknown is whether buy's gateway emits a Schema 2 tag carrying this entry's app code. That question goes to buy or the organisers; it cannot be answered from our side of the wire.

Because there is no backfill, the safe reading remains to tag everything that *can* be tagged. The tag is wired into the Remesso settlement client, which does send transactions. The x402 client built on 2026-11-03 deliberately carries no tag, for the reason above, and says so in its own source. `withAttribution` from `@celo/attribution-tags` and the `celo.dataSuffix` that `loops project get` returns both apply to transactions we send, and this is not one.

The independent-user qualifier excludes wallets created/funded by the entrant and requires earlier Celo activity. The FAQ also welcomes newcomers. Free email registrations are not proof of qualifying independent wallets. Do not invent traction or eligibility. Source: [official rules and FAQ](https://www.loops.house/agents-on-open-rails).
