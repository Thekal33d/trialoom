# UX-01 — A simpler free-beta experience

Date: 2026-11-04 (Africa/Lagos). Decision: D061. Implemented locally; not deployed.

## Problem and resulting experience

The user found Trialoom verbose and confusing for people without technical backgrounds. The public pages mixed the current beta with future marketplace mechanics, authentication had competing marketing headlines, and the workspace asked for details that could be supplied automatically. Test reports foregrounded technical metadata instead of the outcome.

The primary path is now **add a website → run an available test → read the result**. The light paper/forest-green identity is retained, with clearer type hierarchy, open lists, fewer panels and a useful report preview instead of decorative statistics.

| Surface | Change |
| --- | --- |
| Homepage | One concrete promise, one primary action, an explicitly labelled example report, three steps and optional FAQ details. Removed the unmeasured time-saving claim. Availability and signup links still follow server configuration. |
| Signup and sign-in | Compact forms, one heading, shorter explanations, optional wallet login. Email signup names the workspace from the person's name rather than asking another question. |
| Free workspace | “My websites,” a primary Add website action, optional website name, default environment under More options, and explicit permission to test. The sample is a secondary path. |
| Test history | Newest test expanded; older results collapsed. Plain status labels distinguish passed checks from incomplete tests. View replay is visible beside the result; network metadata stays behind Technical details. |
| Suggestions | The next step is prominent and labelled AI suggestion. Supporting observations and the advisory boundary remain available in a disclosure. Advice cannot change the test result. |
| Example report | Leads with the invitation problem and reproduction steps. Original version/Proposed fix comparison shows human outcomes before HTTP codes and build fingerprints. Independent review remains visibly pending. |
| Account/help | Short account settings and three-step help. Future payments sit in a help disclosure. The invited workspace loses its decorative sidebar slogan; its advanced work/review/payment controls remain intact. |

## Interaction and accessibility

- Adding a website focuses its address; cancelling or saving restores focus to Add website when available.
- Saving without a name uses the hostname, bounded to the existing field limit. Permission remains required and the server still rejects private network targets.
- Status polling slows while idle. Refresh failures preserve the last results and cannot erase an unrelated form error.
- Native disclosures work by keyboard. Focus indicators, reduced motion, readable status text and small-screen layouts are preserved.
- “All checks passed” requires a completed result with at least one check and every check passing. A blocked run says “Test incomplete” and does not claim a product defect.
- Replay remains a sanitized action log, explicitly labelled as such, without pretending to be video.

## Verification

The [evidence record](evidence/UX-01.json) contains the final checks and limitations. Browser checks use real application sessions, signatures, routes and disposable database records. The result-presentation check injects controlled read responses for incomplete/passing tests and a suggestion; it is not evidence of a new runner execution or paid provider output.

Initial checks caught insufficient contrast on step numbers and overflow in the 320-pixel report header. Both were corrected before final verification. Existing demo-download assertions still require synthetic labelling, pending independent review and no payment authorization.

Local screenshots are kept under ignored `artifacts/ux-01/` and `test-results/`. These checks are not a usability study with nontechnical users. A real wallet extension/mobile app still needs manual confirmation as recorded in WALLET-01.
